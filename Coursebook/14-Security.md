# 安全 ^security

**黑客就像艺术家，每天心情好时才起床作画** — **弗拉基米尔·普京**

计算机安全指的是保护硬件和软件，使其免遭未授权的访问或篡改。即使你并不直接在计算机安全领域工作，这些概念仍然值得学习，因为只要时间足够，所有系统都会遇到攻击者。尽管这一章是作为独立章节引入的，但需要指出的是，其中大多数概念和代码示例其实早在本课程的其他地方就已经出现过。我们不会深入讨论所有常见的攻击与防御手段，也不会讲如何在一个任意系统上实施这些攻击。我们的目标是让你了解这个领域：如何让程序只做你希望它做的事。

## 安全术语与伦理 ^security-terminology-and-ethics

为了让几乎没有计算机安全经验的人迅速上手，有几个术语需要先解释清楚。

1.  **攻击者（Attacker）**通常指试图侵入系统的用户。所谓侵入系统，是指执行某个系统开发者并未打算让其发生的动作。它也可以指访问你本不该访问的系统。

2.  **防御者（Defender）**通常指阻止攻击者侵入系统的用户。这个人可能就是系统的开发者。

3.  攻击者有不同类型。**白帽（white hat）**黑客是在获得同意的前提下尝试攻破防御者的系统。这通常是一种预防性测试——以防哪天来了一次不那么友好的攻击。**黑帽（black hat）**黑客则是在未经许可的情况下入侵，并且意图把获得的信息用于任何目的。灰帽黑客的不同之处在于，其意图是告知防御者存在某个漏洞——不过这一点有时很难判断。

**“危险，罗宾逊！”** 在让你继续往下读之前，有必要先谈谈伦理问题。在你跳过这一节之前，请记住：你的职业生涯有可能仅仅因为你做的一个不道德的决定而终结。《计算机欺诈与滥用法》（Computer Fraud and Abuse Act，CFAA）是一部范围极广、而且可以说相当糟糕的法律，它把对“受保护计算机”的未授权使用定为犯罪。由于大多数计算机都参与某种跨州／跨国商业活动（互联网），所以大多数计算机都落入这一范畴。在执行任何攻击或防御之前，务必先想清楚自己的行为，并想好一套问责链条。更具体地说，在尝试执行攻击之前，一定要确认你所在组织的上级已经批准。

首先，只要有可能，就从你的上级那里取得书面许可。我们确实意识到这是一种推卸责任的做法，它把责任往上推了一层；但冒昧地讲句愤世嫉俗的话，组织为了避免损失，往往会把责任推到某个具体员工头上 TODO: **Citation Needed**。如果做不到，就按工程流程走。

1.  弄清楚你试图解决的问题是什么。你无法解决一个自己还没有完全理解的问题。

2.  判断你是否真的需要“黑进”这个系统。“hack”一般被定义为试图以非预期的方式使用一个系统。首先，你应当判断你的使用是有意、无意，还是介于两者之间——去问系统所有者。如果问不到，就对“什么才算预期使用”作出合理判断。

3.  对“黑进”这个系统的代价作出合理估算。找几位工程师一起核实这个估算，让他们指出你可能忽略的地方。尽量让有人在这份方案上签字确认。

4.  谨慎执行方案。如果在任何环节看起来不对劲，就停下来，在继续之前重新权衡风险。

如果当前的应用没有明确的伦理准则，那就自己制定一套。这通常被称为一个 `policy vacuum`。这看起来可能像是无用功，也更偏“业务侧”的东西，不太符合计算机科学家的习惯，但这里赌上的是你的职业生涯。作为一名计算专业人员，评估风险并决定是否执行，是你自己的责任。法院通常喜欢援引判例，但你可以很容易地说自己不是法律专家。取而代之的是，你必须能够表明：你的反应是一个“理性”的工程师会有的反应。

### CIA 三要素 ^cia-triad

有三个被广泛接受的目标，可以帮助我们判断一个系统是否安全。

1.  信息保密性（Confidentiality）意味着只有获得授权的各方才允许看到某条信息。

2.  信息完整性（Integrity）意味着只有获得授权的各方才允许修改某条信息，无论他们是否被允许看到它。它确保信息在传输过程中保持完整。

3.  信息可用性（Availability）意味着信息或服务在需要的时候是可用的。

4.  上面这三点共同构成保密性、完整性和可用性（CIA）三要素，通常还会再加上真实性（authenticity）。

其中任何一项被破坏，系统的安全性（无论是一项服务还是一条信息）就已经受到了危及。

## C 程序中的安全 ^security-in-c-programs

### 栈破坏 ^stack-smashing

请考虑下面这段代码。

``` objectivec
void greeting(const char *name) {
  char buf[32];
  strcpy(buf, name);
  printf("Hello, %s!\n", buf);
}

int main(int argc, char *argv[]) {
  if (argc < 2){
    return 1;
  }
  greeting(argv[1]);
  return 0;
}
```

strcpy 完全没有做边界检查！这意味着我们有可能传入一个很长的字符串，让程序做出意料之外的事情，通常的做法是把函数的返回地址替换成恶意代码的地址。大多数字符串只会让程序以段错误退出。

    $ ./a.out john
    Hello, john!
    $ ./a.out JohnAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA...
    Program received signal SIGSEGV, Segmentation fault.
    ...

如果我们以某种方式篡改这些字节，并且程序是用正确的标志位编译的，我们实际上真的能拿到一个 shell！设想一下，如果那个文件属于 root，我们把一段有效的字节码（二进制指令）当作字符串塞进去会发生什么。结果就是，我们会尝试执行 `execve('/bin/sh', ``'/bin/sh', NULL ``, NULL)` 编译出来的操作系统的字节码，并把它作为我们字符串的一部分传进去。运气好的话，我们就能拿到一个 root shell。

    $ ./a.out <payload>
    root#

问题出现了：这破坏了上述三要素中的哪一部分？试着自己回答这个问题。那么我们该怎么修复它？我们可以在 C 语言层面让大多数程序员养成使用 `strncpy` 或 `strlcpy` 的习惯（在 OpenBSD 系统上）。后面会讲到的栈金丝雀（stack canary）同样能解决这个问题。

### 缓冲区溢出 ^buffer-overflow

你们中的大多数人对缓冲区溢出已经很熟悉了！很多时候它们相当温顺，只会导致程序简单崩溃或一些有趣的小错误。这里是一个完整的例子。

    > cat main.c
    #include <stdio.h>

    int main() {
        char out[10];
        char in[10];
        fscanf(stdin, "%s", in);
        out[0] = 'a';
        out[9] = '\0';
        printf("%s\n", out);

        return 0;
    }
    > gcc main.c -fno-stack-protector # need the special flag otherwise won't work
    # Stack protectors are explained later.
    > ./a.out
    hello
    a
    > ./a.out
    hellloooooooo
    aoo
    >

如果你还记得 C 的内存模型，这里发生什么应该就很清楚了。out 和 in 在内存中是紧挨着的。如果你从标准输入读入一个溢出的字符串，那么最后打印出来的就是 aoo。如果代码片段的开头换成下面这样，事情就会稍微严重一点

``` objectivec
int main() {
  char pass_hash[10];
  char in[10];
  read_user_password(pass_hash, 10);
  // ...
}
```

### 乱序执行与 Spectre ^sec-spectre

乱序执行是一项了不起的进展，最近被许多硬件厂商所采用（想想 1990 年代）TODO: **citation needed**。处理器现在不再按顺序执行一系列指令（比如先给一个变量赋值，再给另一个变量赋值），而是会在当前指令完成之前就执行后续指令（<a href="#ref-guide2011intel">[1]</a>）。这是因为现代处理器有大量时间在等待内存访问以及其他 I/O 驱动的操作。这意味着处理器在等待某个操作完成期间，会先把接下来的几个操作执行掉。如果这些操作中任何一个可能改变最终结果，就会有一道屏障（barrier）；或者如果重排序违反了指令间的数据依赖，处理器就会保持指令原有的顺序（<a href="#ref-guide2011intel">[1]</a>）。

自然而然地，这既让 CPU 更节能，能实时执行更多指令，也因复杂架构而增加了安全风险。系统程序员真正担心的是：线程之间带互斥锁的操作会被乱序执行——这意味着一个纯软件的互斥锁实现，如果没有大量内存屏障就会失效。因此，程序员必须意识到：在现代处理器上，如果没有屏障，一系列线程之间的更新可能会被漏掉。

在这方面最突出的 bug 之一就是 Spectre（<a href="#ref-kocher2018spectre">[2]</a>）。Spectre 是一个 bug：由于乱序执行，那些本来不会被执行的指令被推测性地执行了。下面这段代码是一个高层次的概念验证。

``` objectivec
char *a[10];
for (int k = 9; k != 0; --k) {
  a[k] = calloc(1, 1);
}
a[0] = (char *) 0xCAFE;
int val;
int j = 9; // This will be in a register
int i;     // This will be in main memory
for (i = 9; i >= 0; --i, --j) {
  if (i) {
    val = *a[j];
  }
}
```

我们来分析这段代码。第一个循环通过一次合法的 calloc 分配了 9 个元素，`a[1]` 到 `a[9]`。第二个循环访问到的最后一个元素 `a[0]` 是 `0xCAFE`，这意味着解引用它应该会引发 SEGFAULT。第二个循环运行 10 次。在前 9 次迭代中，分支都会被取到，`val` 被赋予一个合法值。有意思的部分发生在最后一次迭代。程序最终的行为是跳过最后一次迭代，因此 `val` 永远不会被赋上那个最后的值。

但在特定的编译条件和编译器标志下，这些指令会被推测性地执行。处理器认为该分支会被取到，因为在前 9 次迭代中它一直被取到。于是处理器会去取那些指令。由于乱序执行，当 *i* 的值正在从内存取回时，我们必须强制它不被放进寄存器。然后处理器就会尝试解引用那个地址，这本应导致 SEGFAULT。但由于程序在逻辑上从未真正到达过该地址，这个结果会被丢弃。

现在，诀窍来了。尽管这次计算的值本应导致 SEGFAULT，这个 bug 却不会清空那块缓存——其中引用了存放 0xCAFE 的物理内存。这不是一个精确的解释，但它基本上就是其工作原理。由于数据仍然留在缓存中，如果你再次诱使处理器利用 `val` 从缓存中读取，你就会读到一个平时无法读取的内存值。它可能包含诸如密码、支付信息等重要内容。

### 操作系统安全 ^operating-systems-security

1.  权限。在 POSIX 系统里，权限无处不在。有些目录你能访问、有些不能；有些文件你能访问、有些不能。每个用户账号对每个文件和目录的访问权，都是通过读-写-执行（RWX）位授予的。用户会被归入所有者、所属组或“其他人”中的某一类，而其对文件的访问范围就由这些位来限制。注意，权限在目录上的行为与在文件上略有不同。

2.  能力（Capabilities）。除了文件权限之外，一个进程还可以被赋予一组特定的能力：它被允许执行的特定特权操作。完整列表可以查阅 capabilities(7)。简而言之，赋予某项能力，就允许用户执行一组动作。例子包括控制网络设备、创建特殊文件，以及窥探 IPC 或进程间通信。

3.  地址空间布局随机化（ASLR）。ASLR 会让进程中若干重要部分的地址空间——包括可执行文件的基地址，以及栈、堆和各个库的位置——在每次运行时都从随机值开始。这样一来，面对一个已在运行的可执行文件，攻击者必须随机猜测敏感信息可能藏在哪里。没有 ASLR 的话，攻击者例如就能轻松发起 `return-to-libc` 攻击，因为每个库函数的地址在每次运行中都是相同的。

4.  栈保护（Stack Protectors）。假设你像前面那样写出了一个缓冲区溢出。多数情况下会发生什么？除非被专门关闭，编译器会插入栈保护器，也就是栈金丝雀。这是一个驻留在栈中、并且在函数调用期间必须保持不变的值。如果该保护器在函数调用结束时被覆盖，运行时就会中止，并向用户报告检测到了栈破坏。

5.  写 xor 执行，也称为 `Data Execution Prevention`（DEP）。这是我们在 IPC 一节中介绍过的一种保护，它把代码和数据区分开来。某个内存页要么可写，要么可执行，但不能两者兼有。这是为了防止这样的缓冲区溢出：攻击者写入任意代码（通常存放在栈或堆上），然后以用户的权限去执行它。

6.  防火墙。Linux 内核提供 netfilter 模块，用来决定是否允许一个进来的连接，并对连接施加各种其他限制。这有助于抵御 DDOS 攻击（后面会讲）。

7.  AppArmor。AppArmor 是一套位于用户态的操作系统工具，用于把应用程序限制在某些操作之内。

OpenBSD 可以说是一个更好的安全系统。它有许多面向安全的特性，其中一些前面已经有所涉及。完整的特性列表见 <a href="https://www.openbsd.org/innovations.html">https://www.openbsd.org/innovations.html</a>。

1.  pledge。Pledge 是一个用于限制系统调用的强大命令。这意味着，如果你有一个像 `cat` 这样只做文件读写的简单程序，那么完全可以合理地限制掉所有网络访问、管道访问以及对文件的写权限。这被称为对一个可执行文件或系统进行“加固”（hardening）的过程：只给运行一个系统所必需的那少数几个可执行文件，分配尽可能少的权限。Pledge 在有人试图实施注入攻击时也很有用。

2.  unveil。Unveil 是一个系统调用，它把当前程序的访问限制在少数几个目录上。这些权限同样适用于所有 fork 出来的程序。这意味着，如果有一个你真想运行的可疑可执行文件，而它的描述是“创建一个新文件并输出随机单词”，你就可以用这个调用把它的访问限制在一个安全的子目录中，并观察它在试图访问根目录下的系统文件时收到 SIGKILL 信号。这对你的程序同样可能有用。如果你希望确保更新过程中不会丢失任何用户数据（Steam 的某次系统更新就发生过这种情况），那么系统可以只暴露出该程序的安装目录。这样即使攻击者在这个可执行文件中找到了漏洞，也只能攻破安装目录。

3.  sudo。Sudo 并不是 OpenBSD 的发明，但它的长期维护者是一位 OpenBSD 开发者，而且它到处都在用！（OpenBSD 本身现在随附了一个更简单的替代品 `doas`。）过去，要以 root 身份运行命令，你必须降权进入一个 root shell。有时这还意味着要给用户一些令人不安的系统能力。Sudo 让你可以一次性地以 root 身份执行命令，而不必给你的所有用户一长串能力。

### 虚拟化安全 ^virtualization-security

虚拟化指的是为某个程序创建一个虚拟版的环境供其运行。虽然随着新一代裸金属虚拟机的出现，这个定义可能需要稍微变通一下，但这个抽象仍然存在。你可以把它想象成每块主板对应一个操作系统。软件意义上的虚拟化，是提供诸如 USB 端口或显示器这类“虚拟”主板外设，让另一个程序（即桥接程序）与真正的硬件通信以完成某项任务。一个简单的例子就是：在你的宿主桌面系统上运行一台虚拟机！你可以启动一整套完全不同的操作系统，它的指令经由另一个程序转发，然后在宿主系统上执行。今天我们使用的虚拟化形式有很多。下面讨论两种流行的形式。一种形式是虚拟机。这些程序模拟*所有*形式的主板外设，从而构成一台完整的机器。另一种形式是容器。容器不是虚拟机：它们不模拟主板外设，而是与宿主操作系统共享同一个内核，并利用内核特性（如命名空间和控制组）来彼此隔离程序。它们比虚拟机轻量得多，但因为与宿主共享同一个内核，所以提供的隔离边界也更弱。

现在，没有安全性就谈不上像样的虚拟化。采用虚拟化的理由之一，是确保被虚拟化的环境不会恶意地泄漏回宿主环境。这里说“恶意”，是因为确实存在一些我们希望加以约束的有意通信方式。下面是通过虚拟化来提供安全性的几个简单例子：

1.  chroot 是一种人为构造的、用于创建虚拟化环境的方式。chroot 是 change root 的缩写。它改变了程序所认为的系统根目录（/）挂载在哪里。例如借助 chroot，可以让一个 hello world 程序以为 `/home/user/` 才是真正的根目录。这样做很有用，因为没有其他文件被暴露出来。之所以说它很人为，是因为 Linux 仍然需要来自其他目录的额外工具（可以想想 C 标准库），比如 `/usr/lib`，这意味着它们仍可能是脆弱的。

2.  命名空间（namespaces）是 Linux 创建虚拟化环境的更好方式。我们不会深入讨论，只需知道它们存在即可。

3.  硬件虚拟化技术。硬件厂商已经越来越意识到，在模拟指令时需要物理层面的保护。因此，用户可以启用一些开关，让操作系统切换到虚拟化模式；在该模式下指令照常运行，同时会被监视是否存在恶意行为。这有助于提升性能，并增强虚拟化环境的安全性。

## 网络安全 ^cyber-security

网络安全可以说是安全领域中最为人熟知的一块。随着我们的系统越来越多地通过 Web 遭到入侵，理解如何防范这些攻击就变得十分重要。

### TCP 层面的安全 ^security-at-the-tcp-level

1.  加密。**TCP 是未加密的！** 这意味着任何通过 TCP 连接发送的数据都是明文。如果需要发送加密数据，就得使用更高层的协议，比如 HTTPS，或者自己开发一套。

2.  身份验证。在 TCP 中没有办法验证你连接的对象是谁。既没有检查机制，也没有联邦数据库。DNS 的应答通常是正确的，但普通 DNS 无法让客户端验证它们。伪造的应答和真实应答一样容易被接受，而程序会欣然连到别人递给它的任意地址上。除了那些拥有已批准白名单或“秘密”连接协议的系统，在 TCP 层面几乎没有什么办法能阻止这种事。

3.  Syn-Ack 序列号。这是一项安全方面的改进。TCP 有我们所谓的序列号特性。这意味着在 SYN-SYN/ACK-ACK 这套握手过程中，连接从一个随机整数开始。这一点很重要：如果攻击者想伪造数据包（假装那些数据包来自你的程序），那他要么得正确猜中——这很难——要么必须处在你的数据包通往目的地的路径上——这要容易得多。ISP 在目的地这一点上帮了点忙，因为他们可能让一个连接经过不同的路由器，这就让攻击者很难待在某个固定位置、并确信自己一定能收到你的数据包——这也是安全专家通常不建议在咖啡馆 Wi-Fi 上处理敏感任务的原因。

4.  Syn 洪泛。在第一个同步包被确认之前，连接并不存在。这意味着一个恶意攻击者可以写一个糟糕的 TCP 实现，向一台毫无防备的服务器倾泻 SYN 包。SYN 洪泛很容易缓解：在流量达到某个阈值并持续一定时间之后，用 IPTABLES 或其他 netfilter 模块丢弃来自该 IP 地址的所有传入连接。

5.  拒绝服务、分布式拒绝服务是最难阻止的一类攻击。如今各家公司仍在努力寻找缓解这类攻击的好办法。它的做法是向服务器转发各式各样的网络流量，指望这些流量能把服务器堵死、拖慢。在大型系统中，这可能导致连锁故障。如果系统设计不当，一台服务器的故障会让其他所有服务器接手更多工作，从而提高它们也发生故障的概率，如此循环下去。

### DNS 层面的安全 ^security-at-the-dns-level

2019 年 1 月，美国国土安全部发布了第 19-01 号紧急指令，要求联邦机构在一波 DNS 基础设施篡改事件之后审计并锁定自己的 DNS 记录 <a href="https://www.cisa.gov/news-events/directives/ed-19-01-mitigate-dns-infrastructure-tampering-closed">https://www.cisa.gov/news-events/directives/ed-19-01-mitigate-dns-infrastructure-tampering-closed</a>。这类攻击利用的是 DNS 自身内置的弱点。DNSSEC 是对 DNS 的扩展，而不是替代品，它让解析器能够验证某个应答确实是由该域的所有者签名的。首先，普通 DNS 对域名请求不提供任何形式的验证。也就是说，伪造 DNS 名字服务器、让它们把你的浏览器指向潜在恶意服务器，是件容易的事。记住，传统的 DNS 请求是以未加密的 UDP 数据包发送的，因而容易被篡改。这意味着，如果攻击者截获了一个发往 DNS 服务器的明文请求，他就可以把结果回送给请求方。如今许多操作系统和浏览器可以改用加密连接来发送 DNS 请求，也就是 DNS-over-TLS（DoT）或 DNS-over-HTTPS（DoH），从而保护请求在前往解析器的途中不被读取或篡改。更常见的是，攻击者不去只针对某一个人，而是连上一个公共 Wi-Fi 热点并污染路由器的缓存——这意味着所有连上来的人查询域名时都会得到一个错误的 IP 地址。如果有人借此冒充大型银行，就可能演变成严重的欺骗攻击。
